# Roboklask: 技術解説 ＆ 最適化詳細

本文書では、Roboklask のファームウェア、通信ブリッジ、およびランタイムスケジューラに実装されている深い技術的最適化について解説します。

---

## 1. Zephyr RTOS 上での極限の超低遅延・高頻度ステップパルス生成

### 課題
標準の Arduino 環境は、単一スレッドで `loop()` をシーケンシャルにループ実行します。しかし、Zephyr RTOS などの OS 上で動作する Arduino コア（Arduino UNO R4 WiFi など）では、`loop()` が `return` して再実行されるまでの間に、システムスレッドの再スケジューリング、シリアルポートのポーリング、その他のハードウェア管理など、**200µs〜1ms 程度のオーバーヘッド**が発生します。

ステップ更新ライブラリ `AccelStepper` は、ポーリング制御モデル（`stepper.run()`）を採用しているため、目標のステップ出力周波数よりも大幅に高い頻度でポーリングする必要があります。1/8ステップ解像度で最大速度 **16,000 steps/sec** を出すためには、最低でも **30kHz 以上**の頻度で `run()` を呼ぶ必要があります。しかし、コアのオーバーヘッドのせいで `loop()` の周回が 1kHz 程度に制限されると、モーター速度は 2,000 steps/sec 未満（這うような遅さ）に頭打ちになってしまいます。

### 解決策
`loop()` の `return` に伴う Arduino コア側のオーバーヘッドを完全に回避するため、`loop()` の内部を **`while(true)` による無限ポーリングループ** にリファクタリングしました。

```cpp
void loop() {
  unsigned long last_yield_ms = 0;

  while (true) {
    // 1. CPUの限界周波数（約100kHz）でステッピングモーターを更新
    xyControl.run();

    unsigned long current_time = millis();

    // 2. 33msに満たない場合は、即座に continue してループ先頭に戻る
    if (current_time - last_update_ms < CYCLE_ms) {
      #if defined(ARDUINO_UNO_Q)
      if (Serial1.available() > 0) {
        safeUpdate();
      }
      // スレッド飢餓防止ガード: 1msに1回だけ OS に処理を明け渡す
      if (current_time - last_yield_ms >= 1) {
        last_yield_ms = current_time;
        k_yield();
      }
      #endif
      continue;
    }
    last_update_ms = current_time;

    // 3. 33ms 周期のメイン制御処理を実行
    ...
  }
}
```

* **結果**: ステップのポーリング周波数が ~1kHz から **~100kHz** へと跳ね上がり、NEMA 17 ステッピングモーターの限界値である **`16,000 steps/sec` (秒速約200mm) の最高速度** と、**`25,600 steps/sec²` の加速度** を一切引っかかることなく滑らかに引き出せるようになりました。
* **スレッド安全性**: 1msに1回だけ `k_yield()` を呼び出すことで、Zephyr RTOS のネットワークやシリアル処理のシステムタスクが確実に実行時間を割り当てられ、ハングアップを完璧に防止しています。

## 2. MessagePack-RPC を介した低遅延 RPC 通信の実現

### 課題
当初、Python側のトラッカーは、目標ストライカー座標（`py2mcu`）と目標ボール座標（`ball`）を別々の RPC 通知として 30Hz 周期で送信していました。これは、115200bps のシリアル通信回線上で **毎秒 60 パケット** を処理することを意味します。マイコン側でのパケット受信・デシリアライズ処理のオーバーヘッドにより受信バッファにパケットが滞留し、Python側の送信を停止してもしばらくロボットが遅れて動き続ける「キューイング遅延（数秒レベル）」が発生していました。

### 解決策
1. **パケットの統合**: 目標座標とボール座標を単一の MessagePack-RPC 呼び出しに統合し、通信パケット数を半減させました。
   ```python
   # Python Driver
   self.bridge.notify("py2mcu", target.x, target.y, ball.x, ball.y)
   ```
2. **同期バッファフラッシュ (`safeUpdate`)**: 非同期スレッドのタスク切り替えによる受信遅延を防ぐため、メインループ内でシリアルデータがあること (`Serial1.available() > 0`) を検知し、同期的に `safeUpdate()` を実行するようにしました。
3. **ステップ数レベルの変化検知フィルタ**:
   カメラの画像認識ノイズ（`0.0001` 程度の微小な座標変動）によって毎サイクル目標座標が書き換わると、`stepper.moveTo()` を呼ぶたびに `AccelStepper` の加減速プロファイルプランナーが再計算されてリセットされてしまいます。これを防ぐため、物理的な「目標ステップ数」が実際に変化したときだけ `moveTo()` を呼ぶガードをクラス内部に組み込みました。
   ```cpp
   long target_s1 = (target_step_x + target_step_y) * resolution;
   long target_s2 = (-target_step_x + target_step_y) * resolution;

   if (target_s1 != last_target_s1 || target_s2 != last_target_s2) {
     stepper1.moveTo(target_s1);
     stepper2.moveTo(target_s2);
     last_target_s1 = target_s1;
     last_target_s2 = target_s2;
   }
   ```
* **結果**: 通信起因の遅延が完全に消失し、ロボットの追従性が Python 側の 33ms 制御周期と完全に同期するようになりました。

## 3. 安全機構（Kinetic Safety） ＆ 境界キャリブレーション

### 課題
H-bot リンク機構において、絶対座標の指定のみでホーミングを行うと、左右のモーターのパルス出力のわずかな非対称によってキャリッジが斜めに傾き、リミットスイッチに衝突するリスクがあります。また、壁からの安全マージンが大きすぎると、ストライカーの盤面での可動域が狭くなってしまいます。

### 解決策
* **相対座標によるホーミング**: ホーミング時の移動には絶対座標指定（`moveTo`）ではなく、相対座標（`move()`）を使用しました。これにより、2つのモーターに完全に同一のステップパルス数が供給され、キャリッジが一切傾くことなくまっすぐ前後に直進します。
* **物理限界とソフト境界マージンの分離**:
  スイッチ衝突から安全に離脱するための物理的な戻り量（`PHYSICAL_BACK = 300` ステップ）と、ゲームのプレイ境界を制限するソフトウェアマージン（`STEP_BACK_X`/`Y = 100` ステップ）を分離定義しました。
  ```cpp
  constexpr int XSTEP = 3100 * 2 + 500 - STEP_BACK_X * 2;
  constexpr int YSTEP = 1500 * 2 + 100 - STEP_BACK_Y;
  ```
  これにより、ソフトウェア原点 `0` はスイッチから 100 ステップ離れた安全な位置にありつつ、プレイ領域自体は限界の広さ（`XSTEP=2900`, `YSTEP=1400`）を確保することができました。
* **動的再キャリブレーション**: プレイ中に激突を検知した場合、システムをシャットダウンするのではなく、安全方向への自動離脱（`escapeX/Y`）を行い、その場で絶対座標を動的に再キャリブレーションしてゲームを中断せずに復帰します。
